## 1. Overview

In adherence to the platform's scientific verification standards, this document establishes the precise technical boundaries, known limitations, and deliberate design tradeoffs of the Phase 2 Expression-Aware SQL and Command Execution analyzers.

Phase 2 replaces rigid AST and regex matching with intraprocedural semantic expression and dataflow analysis. However, it does not claim complete vulnerability coverage across all possible Go idioms or interprocedural call chains.

## 2. Technical Boundaries & Known Limitations

### 2.1 Intraprocedural Dataflow Scope (No Interprocedural Call Chains in Phase 2)
- **Current Capability:** The dataflow engine resolves variable assignments, reaching definitions, and expression trees within the boundary of a single function or method (`intraprocedural`).
- **Limitation:** If a SQL query or command string is constructed inside a helper function (e.g. `query := buildCustomQuery(userInput)`) and passed to an execution sink in a caller, the analyzer cannot trace `userInput` across the function call boundary in Phase 2.
- **Fail-Closed Handling:** Rather than guessing or hallucinating vulnerability, the analyzer classifies such cases as `UNRESOLVED_SQL_CONSTRUCTION` with `StateInsufficientEvidence`.
- **Roadmap Resolution:** Interprocedural call-graph construction and parameter-to-call-site taint propagation are formally scheduled for **Phase 5 (Interprocedural Taint & Dataflow Engine)**.

### 2.2 Third-Party ORM & Query Builder Coverage
- **Current Capability:** Analyzes standard `database/sql` execution APIs (`Query`, `QueryRow`, `Exec`, `Prepare`, and their Context-aware variants) on `*sql.DB`, `*sql.Tx`, `*sql.Conn`, and `*sql.Stmt`.
- **Limitation:** Complex fluent ORMs (`gorm.io/gorm`, `entgo.io/ent`, `bun`, `squirrel`) use custom chained builders (e.g. `db.Where("name = ?", name).Find(&users)`). While simple SQL keywords in chained calls may be recognized, complete ORM method chains are not yet fully mapped.
- **Fail-Closed Handling:** Unrecognized method chains default to `UNRESOLVED_SQL_CONSTRUCTION` or `NON_SQL_EXPRESSION` with counter-evidence where parameterization is evident.

### 2.3 Complex Buffer & Dynamic Transformation Obfuscation
- **Current Capability:** Handles direct string literals, `ast.BinaryExpr` string concatenation (`+`), `fmt.Sprintf` / `fmt.Sprint` formatting, and `strings.Join`.
- **Limitation:** Obfuscated or indirect string assembly patterns:
  - Byte slicing and pointer arithmetic (`unsafe.Pointer`).
  - Iterative byte manipulation via `bytes.Buffer.WriteByte` inside complex loops.
  - Runtime reflection (`reflect.Value.Call`) or encoding formats (`base64.StdEncoding.DecodeString`).
- **Fail-Closed Handling:** Incomplete expression trees fail-closed to `UNRESOLVED` states with explicit limitations recorded in `AnalysisLimitations`.

### 2.4 Offline Type-Checking Degradation
- **Current Capability:** When packages define all internal types or depend on the standard library, `go/types` operates with full type fidelity. When third-party modules are unavailable in an offline sandbox, the symbol table builder degrades gracefully to AST-derived signatures and selector matching.
- **Limitation:** Under type degradation, method sets for interface values defined in external packages cannot be fully verified via type reflection. The analyzer relies on syntactic method names (e.g. `Query`, `Exec`, `Run`) and argument signatures.

### 2.5 Execution Safety & Remediation Gatekeeping
- **Invariant:** Phase 2 introduces **zero** automatic remediation capabilities.
- **Safety Policy:** All security findings (`CategorySecurity`, `SeverityCritical`, `SeverityHigh`) generated by `SQLAnalyzer` and `CommandAnalyzer` remain strictly barred from autonomous execution. They require explicit human investigation or cryptographic simulation tokens (`APPROVAL_REQUIRED`).
